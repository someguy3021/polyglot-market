# Фича: k8s-стенд: деплой стека в локальный кластер

> **Статус:** В РАБОТЕ · **Обновлено:** 2026-10-29

**Суть:** стек маркетплейса (postgres, S3, NestJS, фронт-представители) деплоится в локальный k3d-кластер за Traefik-ingress с readiness/liveness-пробами; управление — явными `pnpm k8s:up` / `k8s:down` / `k8s:status`, дефолтный `pnpm setup/start` путь не затронут.

**Ключевое:** решений в протоколе: 0 · этапов: 4

**Связанное:** [ADR-012](../decisions/adr-012-kubernetes-стенд-локально-kind-в-wsl2-манифесты-cloud-переносимы.md) · ADR-003, 006, 008, 009 · features/05, 15

## 1. Суть и потребители

| Потребитель | Как пользуется |
|---|---|
| Автор | витрина production-grade: k8s, ingress, пробы — для вакансий уровня платформы |
| Рекрутер | видит маршрутизацию 2 бекендов за одним ingress (ADR-006 вживую) и пробы на деплойментах |
| ИИ-скринер | стандартные манифесты Kustomize + идемпотентный `k8s:up` без магии |

## 2. Сценарии

1. `pnpm k8s:up` → кластер k3d в WSL2 (создаётся, если нет), образы импортированы из docker-кэша, манифесты применены, rollout'ы зелёные, миграции+сиды прогнаны против кластерной БД.
2. `http://localhost:8080/` — SPA-фронт; `http://localhost:8080/api/*` — контракт NestJS; оба через Traefik.
3. `pnpm k8s:status` — узлы, поды, сервисы, ingress, healthcheck обоих маршрутов.
4. `pnpm k8s:down` — кластер удалён целиком; повторный `k8s:up` поднимает всё заново (данные теряются — стенд демо-режима).

## 5. НЕ-цели

- Не блокирует публикацию фазы 5 (видео/публикация — автор); k8s-стенд — опциональный слой.
- Service mesh (Istio), multi-node, ArgoCD/GitOps-контроллеры — карго-культ для локальной витрины.
- Персистентность данных между пересозданиями кластера (демо-стенд; для данных — обычный `pnpm infra:up`).
