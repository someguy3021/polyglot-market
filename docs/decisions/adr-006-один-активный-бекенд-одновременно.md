# ADR-006: Один активный бекенд одновременно

> **Статус:** принято · **Дата:** 2026-10-19

**Суть:** Laravel и NestJS — взаимозаменяемые реализации одного сервиса. В каждый момент активен максимум один бекенд; панель не даёт запустить второй; тесты гоняются против каждого по очереди.

**Отвергнуто:** «оба бекенда живут одновременно» — бессмысленно (за портом URL всё равно один), порождает гонки миграций и блокировок БД.

**Связанное:** [ADR-001](adr-001-postgresql-как-единственная-субд-во-всех-режимах.md) · [ADR-007](adr-007-docker-только-комбо-профилями-из-корня-репо.md) · features/06, 14

## Контекст

Исходное ТЗ намекало, что оба бекенда могут быть запущены параллельно (порт 8000 и 3000, фронты переключаются вручную). Решение автора (в. 13): «ой, конечно "один бекенд одновременно"! типо это просто один и тот же сервис на разном написанный».

## Опции

### A. Оба параллельно

- Плюсы: можно сравнивать ответы двумя вкладками.
- Минусы: конкурентные миграции, двойная нагрузка на БД, путаница «кто сейчас писает в orders».

### B. Строго один

- Плюсы: простая модель, честная семантика «реализация сервиса»; переключение = стоп одного, старт другого (данные общие).
- Минусы: нет режима сравнения вживую (не нужен).

## Решение

**Вариант B.** Менеджер процессов держит инвариант «≤1 бекенд»: кнопка старта второго бекенда предлагает остановить первый. Для тестов инварианта нет — CI стартует их последовательно против чистой БД.

## Обоснование

- Домен «один сервис, две реализации» — суть экспоната; параллельность ничего не добавляет.
- Общая БД между сессиями двух бекендов — ключевая демонстрация: заказ, оформленный на Laravel, виден NestJS.

## Последствия

**Позитивные:** нет класса багов «кто мигрировал последним»; панель проста и предсказуема.

**Негативные / риски:**
- Ждём одинаковой схемы от обоих ORM — страхует conformance-слой (ADR-005) и общие миграции (ADR-002).
