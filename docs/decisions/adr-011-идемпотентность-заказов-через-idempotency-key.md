# ADR-011: Идемпотентность заказов через Idempotency-Key

> **Статус:** принято · **Дата:** 2026-10-19

**Суть:** `POST /orders` принимает заголовок `Idempotency-Key` (UUID). Повторный запрос с тем же ключом того же пользователя возвращает исходный заказ, не создавая дубликат. Оба бекенда обязаны; фронты всегда шлют ключ.

**Отвергнуто:** «оверинжиниринг, режем» — автор (в. 20): «оверинжиниринг - НУЖЕН, мы за ним буквально гонимся!».

**Связанное:** [ADR-005](adr-005-conformance-тесты-контракта-в-v1.md) · features/01, 02

## Контекст

Двойной клик «Оформить заказ» или ретрай после таймаута создаёт дубликаты заказов — классическая прод-проблема; её решение в витрине показывает понимание распределённых сценариев.

## Опции

### A. Дедупликация на фронте (кнопка блокируется)

- Плюсы: просто.
- Минусы: не решает ретраи на сетевом уровне; нечего показать в контракте.

### B. Idempotency-Key на стороне API

- Плюсы: каноничный индустриальный паттерн (Stripe-стиль); сюжет для собеседования; тестопригоден.
- Минусы: таблица в схеме + логика в обоих бекендах.

## Решение

**Вариант B.** В общей схеме таблица `idempotency_keys(key, user_id, order_id, created_at, unique(key, user_id))`. Обработка: транзакция — вставка ключа; конфликт → возврат существующего заказа (200, не 409). Conformance-кейс: два одинаковых POST → один заказ, идентичные ответы. TTL ключей — 24 ч (чистка сидом/cron-подобной задачей не нужна в v1).

## Обоснование

- Паттерн заметен скринерам и хорошо объясняется в README.
- Дешёвая реализация в Postgres (unique constraint + upsert).

## Последствия

**Позитивные:** фронты защищены от дублей из коробки; контракт приобретает «взрослую» деталь.

**Негативные / риски:**
- Оба бекенда обязаны honour'ить ключ одинаково — кейс закреплён в conformance (ADR-005), расхождение = красный CI.
