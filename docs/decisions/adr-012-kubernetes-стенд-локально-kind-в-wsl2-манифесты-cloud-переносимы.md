# ADR-012: Kubernetes-стенд локально (kind в WSL2), манифесты cloud-переносимы

> **Статус:** Принято · **Дата:** 2026-10-29

**Суть:** production-grade слой витрины поднимаем в kind-кластере внутри WSL2-docker (тот же демон, что и вся инфра); образы — через локальный registry-контейнер, манифесты — стандартный Kustomize + networking.k8s.io/v1 Ingress + Traefik v3 голыми манифестами, переносимы в облачный k8s как есть.

**Отвергнуто:** k3d — ghcr.io заблокирован на этой машине, его proxy-образ недоступен (эмпирически, 2026-10-29); k3s напрямую в WSL — жизненный цикл вне docker, не убирается одной командой; Minikube — тяжеловеснее при тех же свойствах.

**Связанное:** [ADR-008](./adr-008-медиа-minio-с-первого-дня.md) · [ADR-009](./adr-009-целевая-платформа-wsl2.md) · [ADR-006](./adr-006-один-активный-бекенд-одновременно.md) · features/18

## Контекст

- Фазы 1–5 закрыли «локальную витрину»: `pnpm setup/start`, docker-комбо, E2E 2×7. Для вакансионного экспоната нужен production-grade слой (k8s, балансировка, наблюдаемость) — фаза 6 (решение автора, 2026-10-29).
- Платформа — Windows + WSL2, docker-демон (29.7.2) живёт внутри дистрибутива Ubuntu-24.04; на Windows-стороне docker CLI нет (ADR-009).
- Реестры машины (замер 2026-10-29): docker.io — работает; github.com и dl.k8s.io — работают; **ghcr.io — заблокирован** (`dial tcp ...:443: i/o timeout` на token-запрос); `minio/minio` — по-прежнему не пуллится (ADR-008). Значит, выбор раннера и состав образов зависят от сети.
- Docker 29 использует containerd image store: `kind load docker-image` (docker save → ctr import) на нём сломан — `ctr: content digest ... not found` на любом образе (воспроизведено на postgres и свежих сборках, session 10).
- WSL-гашение: дистрибутив терминируется при отсутствии Windows-клиентов (`scripts/lib/docker.mjs`, якорь `keepWslAlive`) — кластер в том же docker наследует эту болезнь.

## Опции

### A. k3d (k3s в docker) — начальный выбор, отвергнут по факту

- Плюсы: быстрый подъём, встроенные Traefik/local-path, статический бинарник в `~/.local/bin`.
- Минусы, ставшие фатальными: для маппинга портов k3d обязателен контейнер `k3d-proxy` из **ghcr.io** — заблокирован (`docker pull ghcr.io/k3d-io/k3d-proxy:5.8.3` → i/o timeout). Кластер не поднимется даже с ручной заливкой образов.

### B. kind (Kubernetes-in-Docker) — выбран

- Плюсы: все системные образы кластера (etcd, coredns, CNI, storage-provisioner) запакованы в ОДИН образ `kindest/node` с docker.io → после разового пулла (~1.5 ГБ) кластеру не нужен внешний реестр вообще; ingress-порты через extraPortMappings при создании; бинарники kind/kubectl — два статических файла с GitHub/dl.k8s.io (оба досягаемы); де-факто стандарт CI (пригодится для 6.4).
- Минусы: нет встроенного ingress-контроллера — ставим Traefik сами; control-plane стартует медленнее k3s (~60 с).

### C. k3s напрямую в WSL (без docker)

- Плюсы: не зависит от docker-демона и его image store.
- Минусы: жизненный цикл (systemd-сервис или голый процесс) вне docker — `k8s:down` не убирает всё; ломает принцип «инфра — это docker из корня репы» (ADR-007); systemd в WSL капризен.

## Решение

**Вариант B — kind в WSL2-docker.**

- Кластер `polyglot` из `infra/k8s/kind-config.yaml`: extraPortMappings 8080→30080 (Traefik), 55432→30432 (postgres), 59002→30002 (S3); containerdConfigPatches — зеркало `localhost:5001` → `http://kind-registry:5000`.
- Образы приложений — только локальной сборки: build на хосте WSL → tag/push в **локальный registry-контейнер** `kind-registry` (registry:2 из docker.io, подключён к сети kind). Это обход сломанного `kind load` и одновременно канонический рецепт kind для локальных образов.
- Ingress — Traefik v3.3 голыми манифестами (Deployment + RBAC + IngressClass + NodePort + Middleware stripPrefix для `/api`). Минимальные пермиссив-CRD traefik.io — **полный** набор типов, которые смотрит Traefik v3.3: провайдер kubernetescrd ждёт синхронизации информеров по всем, иначе молча не публикует конфиг (диагностика session 10).
- Секреты — k8s Secret из локального `.env` скриптом; миграции/сиды — штатным раннером с хоста через проброшенный :55432/:59002; NestJS пишет в S3 по service DNS, а браузерные URL картинок отдаёт через проброшенный порт (патч `S3_URL_BASE` в `backend/nestjs/src/common/s3.ts`).
- Манифесты без k3s/kind-специфики в нагрузках: Deployment/Service/Ingress/PVC — переносятся в облачный k8s заменой registry-префикса образов и секретов.

## Обоснование

- Единственный вариант, который физически работает на этой машине: ни одного пулла из заблокированных реестров после первичной загрузки kindest/node; всё остальное — локальные сборки и docker.io.
- Ограниченный реестр закольцован на ADR-008 (s3rver вместо minio), а сломанный `kind load` — на канонический registry-рецепт вместо костылей.
- Ingress-маршрутизация на два бекенда даёт живую демонстрацию ADR-006 («один активный бекенд») вместо декларации; `/api`-префикс на ingress решает конфликт SPA-маршрутов с путями контракта (`/cart`, `/orders`, `/admin/*`) без правки бекендов.

## Последствия

**Позитивные:**
- Production-grade слой без облака: кластер, ingress, пробы — локально и бесплатно; CI (6.4) сможет переиспользовать kind как есть.
- Идемпотентный `k8s:up` переживает WSL-гашение: подъём кластера и rollout'ов повторяется скриптом, данные в PVC живут до удаления кластера.
- Локальный registry — переиспользуемая база для 6.2 (HPA/k6) и 6.3 (наблюдаемость).

**Негативные / риски:**
- Разовый пулл kindest/node ~1.5 ГБ (потом кластер создаётся за ~60 с).
- Набор CRD в `infra/k8s/crds/` обязан быть полным и для будущих версий Traefik: новый тип = снова «молчаливый 404» — это задокументированная точка сопровождения стенда.
- Ещё один слой поддержки: команды `pnpm k8s:*` внесены в таблицу «Окружение» AGENTS.md и обязаны оставаться рабочими (как и остальные).
